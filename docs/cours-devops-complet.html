RegistryBibliothèque de recettesDocker Hub
VolumeDisque dur externe-v data:/data

Multi-stage Build

Le multi-stage build crée des images finales légères en séparant l'environnement de build de l'environnement d'exécution.

# Stage 1 : Builder — image lourde avec Node.js (500Mo+)
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build          # Compile le React → HTML/CSS/JS statique

# Stage 2 : Runner — image légère Nginx (20Mo)
FROM nginx:alpine
COPY --from=builder /app/build /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
# Le résultat final ne contient PAS Node.js !
✅ Bénéfice
Image finale : ~20Mo au lieu de ~500Mo. Moins de surface d'attaque, déploiement plus rapide.

Docker Compose

Docker Compose orchestre plusieurs containers interdépendants dans un seul fichier YAML.

version: '3.8'
services:
  mongodb:
    image: mongo:6.0
    volumes:
      - mongodb_data:/data/db   # Persistance des données
    networks: [portfolio_network]

  backend:
    image: anoor9s6/portfolio-backend:latest
    environment:
      MONGODB_URI: mongodb://mongodb:27017/portfolio  # Nom du service !
    depends_on:
      mongodb:
        condition: service_healthy  # Attendre que MongoDB soit prêt
    networks: [portfolio_network]

  frontend:
    image: anoor9s6/portfolio-frontend:latest
    ports:
      - "80:80"
    depends_on: [backend]

volumes:
  mongodb_data:    # Persiste même si le container est supprimé

networks:
  portfolio_network:   # Réseau isolé pour les 3 services

Networking Docker

Les containers d'un même docker-compose.yml se parlent par nom de service, pas par IP. C'est pourquoi le backend utilise mongodb:27017 et non localhost:27017.

[portfolio_network] ├── frontend → peut appeler backend:5000 ├── backend → peut appeler mongodb:27017 └── mongodb → non accessible depuis l'extérieur
⚠️ Erreur classique
Utiliser localhost dans une variable d'environnement d'un container pour pointer vers un autre container. localhost dans un container = le container lui-même, pas un autre service.

Jenkins — Pipeline CI/CD

CI vs CD — Définitions

TermeSignificationCe que ça fait
CIContinuous IntegrationChaque push déclenche build + tests + analyse qualité
CDContinuous DeliveryLe code validé est automatiquement prêt à déployer
CDContinuous DeploymentLe déploiement en prod est aussi automatique

Ton pipeline implémente CI + Continuous Delivery : le déploiement AWS nécessite une approbation manuelle (input), ce qui est une bonne pratique pour la production.

Flux du pipeline

GitHub Push │ ▼ (webhook) Jenkins detecte le push │ ▼ [Checkout] → [SonarQube] → [Quality Gate] │ ▼ (si QG OK) [Build Backend] ══╗ ║ (parallèle) [Build Frontend] ═╝ │ ▼ [Push Docker Hub] │ ├── DEPLOY_TARGET=kubernetes ──────────────────────┐ │ [Terraform Init+Validate] │ │ [Terraform Plan] │ │ [⚠️ Approbation manuelle] │ │ [Terraform Apply] → EC2 AWS │ │ [Deploy K8s] → Docker Desktop │ │ │ └── DEPLOY_TARGET=docker-compose ──────────────────┘ [docker-compose up]

Anatomie du Jenkinsfile

pipeline {
    agent any           // Utilise n'importe quel agent disponible

    parameters {        // Paramètres saisis au lancement
        choice(name: 'DEPLOY_TARGET', choices: ['kubernetes', 'docker-compose'])
        password(name: 'MONGO_PASSWORD', defaultValue: '')
    }

    triggers { githubPush() }   // Déclenché automatiquement par GitHub

    environment {               // Variables disponibles dans tous les stages
        DOCKERHUB_NAMESPACE = 'anoor9s6'
        TF_DIR = 'terraform/scenario1-free-tier'
    }

    stages {
        stage('Build') {
            when { expression { params.DEPLOY_TARGET == 'kubernetes' } }
            parallel {          // Exécution simultanée
                stage('Backend')  { steps { sh '...' } }
                stage('Frontend') { steps { sh '...' } }
            }
        }
    }

    post {
        success { mail to: '...', subject: '✅ ...' }
        failure { mail to: '...', subject: '❌ ...' }
        always  { cleanWs() }   // Nettoyage systématique
    }
}

Gestion des credentials

Les secrets ne doivent jamais apparaître en clair dans le Jenkinsfile. Jenkins les injecte via withCredentials et les masque automatiquement dans les logs.

Type de credentialSyntaxe JenkinsUsage
Username/PasswordusernamePassword(...)Docker Hub
Secret textstring(...)Tokens, mots de passe
Secret filefile(...)kubeconfig, certificats
AWS Credentials$class: 'AmazonWebServicesCredentialsBinding'Access Key + Secret Key AWS
⚠️ Leçon apprise — Styles incompatibles
On ne peut pas mélanger le style $class: (plugin AWS) avec le style natif (string(), usernamePassword()) dans le même withCredentials([...]). Jenkins plante silencieusement sans message d'erreur.

Solution : utiliser deux blocs withCredentials séquentiels, ou utiliser un paramètre pipeline password pour éviter le credential Jenkins.

Images distroless — leçon clé

Certaines images Docker officielles sont distroless : elles ne contiennent que le binaire principal, sans shell, sans gestionnaire de paquets, sans rien d'autre. C'est plus sécurisé mais impose des contraintes.

ImageTypeProblème rencontréSolution
bitnami/kubectlDistrolessunknown command "sh"Utiliser alpine/k8s qui inclut un shell
hashicorp/terraformContient /bin/shno command "sh" car entrypoint=terraform--entrypoint /bin/sh ou installer terraform directement sur l'agent
Chapitre 4

SonarQube — Qualité du code

Qu'est-ce que l'analyse statique ?

L'analyse statique examine le code source sans l'exécuter. Elle détecte les problèmes de qualité, les failles de sécurité et les mauvaises pratiques en analysant la structure du code.

Les 4 catégories SonarQube

CatégorieDescriptionExemple
🐛 BugCode qui va probablement planterVariable utilisée avant d'être définie
🔒 VulnerabilityFaille de sécurité connueMot de passe en dur dans le code
🔧 Code SmellCode qui fonctionne mais difficile à maintenirFonction de 500 lignes
📋 DuplicationCode copié-colléMême logique dans 5 endroits

Quality Gate

Le Quality Gate est un ensemble de conditions qui doivent être respectées pour que le code soit considéré comme acceptable. Dans ton pipeline :

stage('Quality Gate') {
    steps {
        timeout(time: 5, unit: 'MINUTES') {
            waitForQualityGate abortPipeline: true  // Bloque si QG échoue
        }
    }
}

Si le Quality Gate échoue → le pipeline s'arrête → les images Docker ne sont pas buildées → rien n'est déployé. C'est le comportement voulu : on ne déploie jamais du code de mauvaise qualité.

Configuration dans ton projet

Le fichier sonar-project.properties à la racine configure l'analyse :

sonar.projectKey=anoors_portfolio_react
sonar.sources=src,backend
sonar.exclusions=**/node_modules/**,**/build/**,**/dist/**
sonar.host.url=http://sonarqube:9000
ℹ️ Langages analysés dans ton projet
JavaScript/JSX (React + Node.js) · CSS · JSON · Dockerfile — soit 25 fichiers source lors des derniers builds.
Chapitre 5

Kubernetes — Orchestration de containers

Pourquoi Kubernetes ?

Docker Compose est excellent en développement. En production, il manque :

BesoinDocker ComposeKubernetes
Redémarrage auto si crash✅ (restart: unless-stopped)✅ natif
Scaling horizontal❌ manuel✅ replicas: 3
Rolling update sans downtime❌✅ natif
Load balancing❌✅ via Services
Multi-nœuds❌✅ cluster
Health checks avancés✅ basique✅ liveness + readiness

Concepts fondamentaux

Pod

La plus petite unité Kubernetes. Un pod encapsule un ou plusieurs containers qui partagent le même réseau et le même stockage. En pratique : 1 pod = 1 container applicatif.

Deployment

Gère un ensemble de pods identiques (replicas). Garantit que le nombre désiré de replicas tourne en permanence. Gère les rolling updates.

spec:
  replicas: 2                    # Toujours 2 pods actifs
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                # Max 1 pod supplémentaire pendant la MAJ
      maxUnavailable: 0          # Jamais de pod indisponible → zéro downtime

Service

Expose des pods sur le réseau avec une IP stable. Les pods peuvent changer d'IP à chaque redémarrage, le Service reste stable.

TypeAccèsUsage dans ton projet
ClusterIPInterne au cluster uniquementBackend (port 5000)
LoadBalancerIP externeFrontend (port 80)
NodePortPort du nœudNon utilisé

Namespace

Espace d'isolation logique. Ton application tourne dans le namespace portfolio, séparé du namespace kube-system (composants Kubernetes internes).

Ingress

Reverse proxy HTTP au niveau du cluster. Une seule IP publique, le routage est basé sur le chemin URL :

/ → portfolio-frontend-service:80
/api → portfolio-backend-service:5000

Architecture K8s du projet

Internet │ ▼ [Ingress : portfolio-ingress] │ ├── / → Service: portfolio-frontend-service (LoadBalancer :80) │ └── Pod frontend #1 (Nginx + React) │ └── Pod frontend #2 (Nginx + React) │ └── /api → Service: portfolio-backend-service (ClusterIP :5000) └── Pod backend #1 (Node.js) └── Pod backend #2 (Node.js) └── → MongoDB (StatefulSet, PVC 5Go) Namespace: portfolio Cluster: Docker Desktop (kind, 2 nodes)

Liveness vs Readiness Probe

ProbeQuestion poséeAction si échec
livenessProbeLe container est-il encore vivant ?Redémarrer le container
readinessProbeLe container est-il prêt à recevoir du trafic ?Retirer du load balancer

Rolling Update — comment ça marche

Quand tu exécutes kubectl rollout restart deployment/portfolio-backend :

Avant : [Pod v1] [Pod v1] Étape 1 : Créer [Pod v2] → [Pod v1] [Pod v1] [Pod v2] Étape 2 : [Pod v2] est Ready → supprimer un [Pod v1] → [Pod v1] [Pod v2] Étape 3 : Créer [Pod v2'] → [Pod v1] [Pod v2] [Pod v2'] Étape 4 : [Pod v2'] est Ready → supprimer [Pod v1] → [Pod v2] [Pod v2'] Après : [Pod v2] [Pod v2'] ← Zéro downtime !

Terraform — Infrastructure as Code

Le problème que Terraform résout

Sans TerraformAvec Terraform
Infrastructure créée manuellement dans la console AWSInfrastructure définie en code HCL
Non reproductible (qui se souvient de tous les clics ?)Reproductible à l'identique en 2 min
Non versionnable (pas d'historique)Git : historique complet des changements
Non collaboratifToute l'équipe voit l'infrastructure
Destruction manuelle et risquéeterraform destroy en une commande

Cycle de vie Terraform

terraform init │ → Télécharge les providers (AWS, TLS, local...) │ → Configure le backend (S3 ou local) ▼ terraform validate │ → Vérifie la syntaxe HCL │ → Vérifie la cohérence des références entre ressources ▼ terraform plan │ → Compare l'état désiré (code) avec l'état réel (tfstate) │ → Affiche un diff : + créer, ~ modifier, - détruire │ → NE CRÉE RIEN — c'est un dry-run ▼ terraform apply │ → Exécute le plan │ → Met à jour le tfstate │ → Crée/modifie/détruit les ressources réelles ▼ terraform destroy └ → Détruit toutes les ressources du tfstate

Le State — concept central

Le fichier terraform.tfstate est la mémoire de Terraform. Il mappe chaque ressource du code à sa contrepartie réelle dans AWS (avec son ID, ses propriétés, ses dépendances).

❌ Ne jamais faire
Committer terraform.tfstate dans git. Il contient des données sensibles : IPs, ARNs, parfois des mots de passe en clair. Leçon apprise sur ce projet : les fichiers tfstate ont été trouvés dans le repo et supprimés via git rm --cached.

Remote State (S3 + DynamoDB)

Pour les équipes, le state doit être centralisé et verrouillé :

terraform {
  backend "s3" {
    bucket         = "anoors-portfolio-tfstate-123456789"  # S3 versionné + chiffré
    key            = "scenario1/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "anoors-portfolio-terraform-locks"    # Verrou = 1 apply à la fois
  }
}
RessourceRôle
S3 Bucket (versionné)Stocke le tfstate. Le versioning permet de revenir à un état précédent.
S3 Bucket (chiffré AES-256)Protège les secrets contenus dans le state
DynamoDB TableLock distribué : empêche 2 terraform apply simultanés

Structure des fichiers Terraform

FichierRôle
provider.tfDéclare les providers (AWS, TLS...) et leurs versions
variables.tfDéclare les variables avec leur type et leur validation
terraform.tfvarsValeurs concrètes des variables — NE PAS COMMITTER
terraform.tfvars.exampleTemplate sans secrets — committable

outputs.tfValeurs exportées après l'apply (IP, URL, commande SSH...)

Docker Hub — le lien entre Jenkins et les cibles

Docker Hub est le registre d'images. Jenkins construit et pousse, les cibles de déploiement pullent. C'est ce qui rend le déploiement indépendant de Jenkins : AWS et Kubernetes récupèrent toujours la dernière version validée.

ℹ️ Stratégie de tags
Deux tags sont poussés pour chaque build :
  • v1.0.250 — tag versionné (immuable, lié au numéro de build Jenkins)
  • latest — toujours la dernière version (utilisé par K8s avec imagePullPolicy: Always)

Notifications par email

Le bloc post envoie un email à chaque fin de pipeline :

  • ✅ Succès : job name, numéro de build, durée, URL Jenkins
  • ❌ Échec : mêmes infos + lien direct vers les logs
  • 🔄 Toujours : cleanWs() nettoie le workspace

Pattern récurrent — images distroless

⚠️ Règle à retenir
Avant d'utiliser une image Docker pour exécuter des commandes shell dans un pipeline, vérifier qu'elle contient un shell : 
docker run --rm image:tag sh -c "echo ok"
Si ça renvoie une erreur, l'image est distroless. Solutions :
  • Chercher une variante avec -alpine ou -slim
  • Installer l'outil directement sur l'agent Jenkins
  • Utiliser --entrypoint /bin/sh si le shell existe mais n'est pas l'entrypoint par défaut

Pattern récurrent — secrets Jenkins dans docker run

⚠️ Règle à retenir
withCredentials([file(..., variable: 'MY_FILE')]) crée un dossier temporaire, pas un fichier. La variable pointe vers le dossier parent.

Pour passer un fichier secret à un container Docker : 
KUBE_FILE=$(find "$KUBECONFIG_FILE" -type f | head -1)
KUBECONFIG_B64=$(base64 -w 0 "$KUBE_FILE")
docker run -e KUBECONFIG_B64="$KUBECONFIG_B64" ...
# Dans le container :
echo "$KUBECONFIG_B64" | base64 -d > /tmp/kubeconfig
