Chapitre 1

Vue d'ensemble

Pourquoi monitorer ?

Sans monitoring, tu découvres les pannes quand les utilisateurs se plaignent. Avec ce stack, tu sais en temps réel ce qui se passe dans ton application.

Sans monitoringAvec ce stack
Panne découverte par les utilisateursAlerte automatique après 1 minute
Impossible de savoir si l'app est lenteLatence P95 visible en permanence
Mémoire qui fuit sans le savoirGraphique heap Node.js en temps réel
MongoDB déconnecté = app silencieusement casséeJauge CONNECTÉ / DÉCONNECTÉ
CPU à 100% détecté trop tardAlerte dès 80% pendant 5 minutes

Les 3 couches d'observabilité

┌──────────────────────────────────────────────────┐ │ MÉTRIQUES (Prometheus + Grafana) │ ← Ce guide │ "Que se passe-t-il en chiffres ?" │ │ → req/s, latence, CPU, RAM, erreurs... │ ├──────────────────────────────────────────────────┤ │ LOGS (docker-compose logs) │ │ "Que s'est-il passé exactement ?" │ │ → Texte horodaté : erreurs, stack traces │ ├──────────────────────────────────────────────────┤ │ TRACES (non implémenté) │ │ "Quel chemin a suivi cette requête ?" │ │ → Latence par étape : API → MongoDB → réponse │ └──────────────────────────────────────────────────┘

Qu'est-ce qu'une métrique ?

Une métrique est une mesure numérique horodatée. Par exemple :

# À 20h50:15, le backend a reçu 42 requêtes GET /api/projets avec status 200
http_requests_total{method="GET",route="/api/projets",status_code="200"} 42

# À 20h50:15, la mémoire heap utilisée est 19.2 Mo
nodejs_heap_size_used_bytes 20132864

Prometheus collecte ces valeurs toutes les 15 secondes et les stocke dans une base de données temporelle. Grafana les lit et les affiche sous forme de graphiques.

Les 4 types de métriques Prometheus

TypeAnalogieExemple dans ce projet
CounterCompteur kilométrique — ne fait que monterNombre total de requêtes HTTP reçues
GaugeThermomètre — monte et descendMémoire heap utilisée, statut MongoDB
HistogramDistribution en tranchesDurée des requêtes (buckets 10ms, 100ms...)
SummaryPercentiles pré-calculésNon utilisé directement ici

Fonctionnement du scrape (Pull model)

Prometheus fonctionne en mode pull : c'est lui qui va chercher les métriques chez les cibles à intervalles réguliers, pas les cibles qui lui envoient des données. C'est l'inverse de la plupart des systèmes de logs.

ℹ️ Pourquoi le mode Pull ?
Si une cible tombe en panne et arrête d'envoyer des données (mode push), Prometheus ne le saurait pas. En mode pull, si Prometheus ne reçoit pas de réponse → la cible est marquée DOWN → alerte déclenchée.

CibleIntervalleRaison

Node Exporter15 secondes (défaut)Métriques système — évolution lente

Chapitre 3

Composants du stack

Prometheus prom/prometheus:v2.51.2

Base de données de séries temporelles spécialisée pour les métriques. Stocke les données pendant 15 jours, évalue les règles d'alerte, expose une API pour Grafana.

FichierRôle
monitoring/prometheus/prometheus.ymlConfiguration principale : cibles, intervalles, fichiers de règles
monitoring/prometheus/rules/alerts.yml7 règles d'alerte avec conditions et sévérités

Grafana grafana/grafana:10.4.2

Interface de visualisation. Se connecte à Prometheus comme datasource et affiche les données en dashboards. Entièrement provisionnée en code — aucun clic nécessaire au démarrage.

FichierRôle
monitoring/grafana/provisioning/datasources/prometheus.ymlDatasource Prometheus auto-configurée au démarrage
monitoring/grafana/provisioning/dashboards/dashboard.ymlProvider : surveille le dossier dashboards/
monitoring/grafana/dashboards/backend-dashboard.jsonDashboard applicatif Node.js
monitoring/grafana/dashboards/system-dashboard.jsonDashboard infrastructure Docker + hôte

cAdvisor gcr.io/cadvisor/cadvisor:v0.49.1

Container Advisor by Google. S'exécute avec accès privilégié aux cgroups Linux pour collecter les métriques de chaque container Docker : CPU, mémoire, réseau, disque.

⚠️ Accès privilégié
cAdvisor nécessite privileged: true et des montages en lecture seule sur /proc, /sys, /var/lib/docker. C'est normal et requis pour lire les métriques kernel.

MongoDB Exporter percona/mongodb_exporter:0.40.0

Traduit les statistiques internes de MongoDB (via db.serverStatus()) en métriques Prometheus : connexions actives, opérations par type, taille des collections, état de réplication.

Node Exporter prom/node-exporter:v1.7.0

Collecte les métriques du système d'exploitation hôte : utilisation CPU par cœur, mémoire RAM/swap, espace disque, trafic réseau, charge système.

prom-client v15.1.3

Bibliothèque Node.js officielle pour exposer des métriques Prometheus. Installée dans le backend Express, elle fournit :

  • Métriques automatiques : heap, CPU, event loop, handles actifs
  • API pour créer des métriques custom : Counter, Gauge, Histogram, Summary
  • Registry : collection de toutes les métriques, exposée sur /metrics
Chapitre 4

Installation et démarrage

Prérequis

  • Docker Desktop installé et démarré
  • Le projet cloné sur release/v1.0.0-cicd-infra
  • Aucune autre application utilisant les ports 3001, 9090, 9100, 9216, 8081

Démarrage du stack complet

# 1. Se placer dans le projet
cd C:\anoors\codes\anoors_portfolio_react

# 2. Rebuilder le backend (prom-client doit être dans l'image)
docker-compose build backend

# 3. Démarrer tous les services
docker-compose up -d

# 4. Vérifier l'état de chaque container
docker-compose ps

✅ Si tout est vert

Commandes de gestion quotidienne

# Redémarrer uniquement le monitoring
docker-compose restart prometheus grafana

# Voir les logs de Prometheus en temps réel
docker-compose logs -f prometheus

# Voir les logs de Grafana
docker-compose logs -f grafana

# Recharger la config Prometheus sans redémarrer
curl -X POST http://localhost:9090/-/reload

# Arrêter tout sans perdre les données
docker-compose stop

# Tout supprimer incluant les volumes (réinitialisation complète)
docker-compose down -v
Chapitre 5

Métriques exposées

Backend Node.js — Métriques custom

Définies dans backend/server.js via prom-client.

http_requests_total (Counter)

Compte chaque requête HTTP reçue depuis le démarrage du serveur.

LabelValeurs possiblesDescription
methodGET, POST, PUT, DELETEMéthode HTTP de la requête
route/api/projets, /metrics, /api/testChemin de l'URL
status_code200, 201, 404, 500...Code de réponse HTTP
# Exemple de valeur brute
http_requests_total{method="GET",route="/api/projets",status_code="200"} 42

# PromQL : taux de requêtes par seconde
rate(http_requests_total[1m])

# PromQL : uniquement les erreurs
rate(http_requests_total{status_code=~"5.."}[5m])

http_request_duration_seconds (Histogram)

Mesure la durée de chaque requête et la répartit dans des buckets temporels.

Bucket le=Requêtes répondant en moins de...
0.0110 millisecondes
0.0550 millisecondes
0.1100 millisecondes
0.3300 millisecondes
0.5500 millisecondes
11 seconde
22 secondes
55 secondes
# PromQL : latence P95 (95% des requêtes sous ce seuil)
histogram_quantile(0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

# PromQL : latence moyenne
rate(http_request_duration_seconds_sum[5m])
/ rate(http_request_duration_seconds_count[5m])

mongodb_connection_status (Gauge)

ValeurSignificationImpact
1ConnectéL'application fonctionne normalement
0DéconnectéAucune lecture/écriture possible en base

Métriques cAdvisor (Docker)

# CPU par container (%)
sum by(name) (rate(container_cpu_usage_seconds_total{name!=""}[1m])) * 100

# RAM par container (Mo)
container_memory_usage_bytes{name!=""} / 1024 / 1024

# Trafic réseau entrant (octets/s)
rate(container_network_receive_bytes_total{name!=""}[1m])

# Trafic réseau sortant (octets/s)
rate(container_network_transmit_bytes_total{name!=""}[1m])

Métriques Node Exporter (Système hôte)

# CPU utilisé (%) — toutes les cibles
100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# RAM disponible (Go)
node_memory_MemAvailable_bytes / 1024 / 1024 / 1024

# Espace disque disponible
node_filesystem_avail_bytes{fstype!="tmpfs"}

# Trafic réseau hôte entrant (octets/s)
rate(node_network_receive_bytes_total[1m])
